# sing-box 1.15 / sing-tun / mihomo Alpha: what to adopt in Segue Core

Engineering study, 2026-11-17. Scope: techniques in sing-box 1.15 alpha, the new
in-house `sing-tun` TCP/IP stack, and mihomo Alpha that matter for a
memory-bounded iOS/Android VPN-extension client core, compared against Segue
Core at `ef16ceca`.

Segue paths are relative to this repository. Two data planes exist and they are
**not** the same code:

- **Production**: `crates/segue-engine/src/tun.rs` (9 342 lines) drives smoltcp
  directly; `crates/segue-engine/src/tun_fd.rs` pumps the platform fd;
  `crates/segue-tun/src/lib.rs` is the bounded packet queue.
- **Prototype**: `crates/segue-kernel/` is a separate, `publish = false` crate
  (`crates/segue-kernel/Cargo.toml:9`) that no other crate depends on. It has
  the more interesting memory design (a shared 4 KiB block pool, elastic ring
  growth) but is not wired into the engine. Recommendations below say which
  plane they target.

## 1. TUN data plane

### 1.1 What sing-tun does

**Architecture.** `sing-tun` is one Go package with four stack backends behind
`NewStack` (`stack.go:47-69`): `go` (the new in-house stack), `gvisor`,
`system`, `mixed`. sing-box selects it from `tun.stack`
(`protocol/tun/inbound.go:494-510`); `stack` is deprecated in favour of the
default `go` stack (`protocol/tun/inbound.go:84-86`). `Go.Start` creates one
`goEngine` per platform queue (`stack_go.go:152-158`), each with its own timer wheel
(`stack_go_wheel.go:8-14`, 1 ms tick) and its own UDP NAT shard.

**Apple utun batching.** This is the most directly copyable part.

- `UTUN_OPT_MAX_PENDING_PACKETS` is set to a value derived from the socket
  receive buffer, not a constant: `pending = receiveBuffer/8*7/(mtu+4)`,
  clamped to `utunMaxPendingPackets = 64` (`tun_darwin.go:371-374`). The
  receive buffer is raised toward 8 MiB and halved down to 1 MiB until
  `SO_RCVBUF` succeeds (`tun_darwin.go:350-354`, `:381-394`). The comment at
  `tun_darwin.go:367-370` explains why: the utun control socket drops outbound
  packets with `ENOBUFS` at `SO_RCVBUF`, whereas hitting the pending-packet
  limit *pauses* the interface instead of dropping.
- Reads use `recvmsg_x` with an adaptive batch: `goReadBatch` = 64 (32 on iOS),
  starting at `goReceiveBatchMin` = 8 (4 on iOS) and doubling when the batch
  fills, halving when it is under half full (`stack_go_io_darwin.go:316-343`,
  `stack_go_profile_default.go:13-14`, `stack_go_profile_ios.go:11-12`).
- Writes use `sendmsg_x` in batches of `goDarwinTransmitBatch = 64`
  (`stack_go_io_darwin.go:23`), but only frames that fit a 4 KiB mbuf cluster
  are batched (`goDarwinBatchFrameLimit = 4096 - PacketOffset`,
  `stack_go_io_darwin.go:30`); larger frames fall back to per-frame `writev`.
  A "gate" keeps the estimated utun input chain under
  `net.utun.max_pending_input` (512) because exceeding it leaks an mbuf per
  rejected write (`stack_go_io_darwin.go:32-45`, `tun.go:130`).
- Buffers are not `sync.Pool`-ed on the Darwin read path. `goReadSlots` holds a
  fixed `[]*buf.Buffer` over one mmap'd region, and pages are parked/reused with
  `madvise(MADV_FREE_REUSABLE)` / `MADV_FREE_REUSE`
  (`stack_go_memory.go:38-113`, `stack_go_memory_darwin.go:7-17`).

**Linux.** GSO/GRO is a WireGuard-derived implementation
(`tun_offload_linux.go:1-4`): `gsoMaxSize = 65536`, `idealBatchSize = 128`
(`:24-27`), virtio-net header, TCP and UDP GRO tables. Multi-queue opens
`IFF_MULTI_QUEUE` with one queue per `GOMAXPROCS`
(`tun_linux.go:110-116`, `stack_go_io_linux.go:75-80`). The Go stack transmits
from per-connection goroutines on Linux (`goEngineTransmits = false`,
`stack_go_io_linux.go:21`).

**TCP stack.** The `go` stack is a port of the Linux TCP state machine, stated
in the file headers (`stack_go_tcp_ack.go:11`, `stack_go_tcp_cong.go:9`,
`stack_go_tcp_rate.go:5`). Concretely:

- Window scaling: local shift 7 (`goLocalWindowShift = 7`,
  `stack_go_conn.go:47`), so the advertised window can reach 8 MiB; bound is
  `min(receiveCapacityMax, 0xffff<<7)` (`stack_go_conn.go:354-359`).
- SACK: negotiated, up to 4 blocks received / 3 sent
  (`goMaxSackBlocks = 4`, `goMaxSackBlocksSent = 3`, `stack_go_ring.go:588-590`),
  with DSACK and reneging handling (`stack_go_tcp_ack.go:239`,
  `stack_go_tcp_cong.go:346-357`).
- Loss recovery: RTO floor 300 ms, initial 1 s, max 60 s
  (`stack_go_tcp_input.go:19-44`), RACK (`goRackRecoveryThreshold = 16`,
  `stack_go_tcp_cong.go:36-37`), F-RTO and DSACK undo
  (`stack_go_tcp_cong.go:380`, `:450-459`), a delivery-rate estimator
  (`stack_go_tcp_rate.go`), and pacing (`stack_go_tcp_cong.go:30-35`).
- Congestion control: `reno`, `cubic`, `bbr`, default cubic
  (`stack_go_tcp_cong.go:126-140`). sing-box never sets
  `TCPCongestionControl`, so cubic is always used in practice.
- Out-of-order data is written into a slab chain at absolute offsets and
  tracked by a fixed 32-range set (`goMaxOOORanges = 32`,
  `stack_go_ring.go:597`); a segment is dropped when
  `oooRanges.bytes() + len > receiveCapacity` (`stack_go_tcp_input.go:639-643`).

**Per-flow memory.** Two build profiles, `!ios` and `ios`
(`stack_go_profile_default.go:7-19`, `stack_go_profile_ios.go:5-17`):

| Constant | default | iOS |
| --- | --- | --- |
| `goReceiveCapacityBase` | 64 KiB | 32 KiB |
| `goReceiveCapacityMax` | 4 MiB | 256 KiB |
| `goTransmitCapacityMax` | 2 MiB | 512 KiB |
| `goEngineBurstBytes` | 1 MiB | 256 KiB |
| `goFlowCapacity` | 16 384 | 1 024 |
| `goReadBatch` | 64 | 32 |
| `goDescriptorRingCapacity` | 2 048 | 512 |
| `goReassemblyEntries` | 8 | 4 |
| `goSlabPoolLowWater` | 128 | 8 |

Receive capacity auto-tunes between base and max, and shrinks back to base when
the slab pool is under pressure (`stack_go_tcp_input.go:833-866`). There is
**no global byte budget** for the stack: the only bounds are the per-connection
caps, slab-pool pressure sharing (`stack_go_ring.go:19-65`) and the UDP NAT
entry count (4 096 on iOS, 16 384 elsewhere, `udp_nat.go:114-121`).

### 1.2 What Segue does today

- **Apple fd path**: `crates/segue-engine/src/tun_fd.rs`. Reads are one
  `read(2)` per packet into a 64 KiB arena (`TUN_FD_READ_ARENA_MIN`,
  `tun_fd.rs:80`, `PacketReader` at `:480-509`); writes are batched up to
  `TUN_FD_WRITE_BATCH_MAX_PACKETS = 128` (`tun_fd.rs:75`) but issued as one
  `write`/`writev` per packet (`write_packet_batch`, `tun_fd.rs:575-625`).
  There is no `recvmsg_x`/`sendmsg_x` and no `UTUN_OPT_MAX_PENDING_PACKETS`
  tuning anywhere in the tree (grep for both returns nothing).
- **Apple packet-pump path**: `platform/apple/Sources/XrayMobileAdapter/XrayPacketTunnelPump.swift`
  polls `NEPacketTunnelFlow` 64 packets at a time (`:145`, `:192`).
- **Linux/Android**: raw-IP fd framing only; no `IFF_VNET_HDR`, no GSO/GRO, no
  `IFF_MULTI_QUEUE` (grep for `TUNSETOFFLOAD`, `IFF_VNET_HDR`,
  `MULTI_QUEUE` returns nothing).
- **TCP stack**: smoltcp 0.14.0 (`Cargo.toml:80`, vendored at `vendor/smoltcp`).
  Sockets are created with a 32 KiB send buffer and a receive buffer of
  `max(32 KiB, 4 × MSS)` (`TCP_BUFFER_SIZE`, `tun.rs:71`;
  `tcp_rx_buffer_size`, `tun.rs:5623`; `add_tcp_listener`, `tun.rs:5635-5655`).
  Congestion control is explicitly **off** (`CongestionControl::None`,
  `tun.rs:5648`) because the socket terminates the local TUN link.
- **Window scaling**: smoltcp fixes the shift at socket creation from the
  receive capacity (`vendor/smoltcp/src/socket/tcp.rs:613`, `:1002`), so a
  32 KiB buffer means shift 0 and a 64 KiB ceiling. The kernel prototype
  documents this limit explicitly (`crates/segue-kernel/src/tun.rs:133-135`,
  `MAX_RING = 64 * 1024`).
- **SACK**: smoltcp supports it, but the reassembly assembler holds only
  `ASSEMBLER_MAX_SEGMENT_COUNT = 4` disjoint ranges
  (`vendor/smoltcp/src/lib.rs:152`), and the vendored patch reports at most
  three SACK blocks (`vendor/smoltcp/XRAY-PATCH.md`).
- **Per-flow memory**: `TcpRemoteBufferPolicy` / `FlowBudgetPolicy`
  (`tun.rs:142-270`). Mobile: 4 MiB per flow normal / 2 MiB under pressure,
  pressure starts at 24 MiB total, hard cap 40 MiB, 256 TCP flows, 512 UDP
  flows (`tun.rs:150-222`). Low-memory: 1 MiB per flow, 20 MiB hard cap, 128
  TCP flows (`tun.rs:246-260`). This is a *remote-buffer* budget layered on
  top of smoltcp's fixed 32 KiB rings, not a single pool.
- **Queue bounds**: `segue-tun` bounds each queue by both depth and bytes
  (`QUEUE_BYTES_PER_SLOT = 1500`, `crates/segue-tun/src/lib.rs:20`;
  `push_packet` at `:973-1003`). Mobile queue depths are 1 024 in / 4 096 out
  (`crates/segue-engine/src/lib.rs:52-53`).
- **Kernel prototype** (not wired): a 4 KiB block `BufferPool` with an 80 %
  high-water admission mark, rings that start at 4 KiB and double to 64 KiB,
  and a stated worst case of ≈13.1 MiB (`crates/segue-kernel/src/tun.rs:39-70`,
  `:150-200`, `:430-480`). The defaults are `tcp_rx_buffer`/`tcp_tx_buffer`
  64 KiB and a 6 MiB pool (`crates/segue-kernel/src/tun.rs:469-480`).

### 1.3 Gap

1. **Apple syscall batching.** Segue issues one syscall per packet in both
   directions. sing-tun's `recvmsg_x`/`sendmsg_x` batching is the single
   largest per-packet CPU win on iOS, and the `UTUN_OPT_MAX_PENDING_PACKETS`
   tuning changes the failure mode from silent `ENOBUFS` drops to interface
   back-pressure.
2. **Linux GSO/GRO.** Segue has none. On Android this costs a syscall per
   packet and prevents TSO-sized writes.
3. **TCP receive window.** Segue's 32 KiB smoltcp ring with shift 0 caps a
   single flow's throughput at `32 KiB / RTT`; at 100 ms that is ≈2.6 Mbit/s
   per flow. sing-tun advertises up to 8 MiB with shift 7 and auto-tunes.
   Segue's kernel prototype documents the same smoltcp constraint and caps its
   rings at 64 KiB for that reason (`crates/segue-kernel/src/tun.rs:133-135`).
4. **Reassembly depth.** 4 disjoint ranges vs sing-tun's 32. On lossy mobile
   paths this shows up as spurious retransmits.
5. **Memory accounting.** Segue's engine has a remote-buffer budget but the
   smoltcp rings are fixed and unaccounted; the kernel prototype has the right
   shape (one pool, elastic rings) but is not the production path.

### 1.4 Recommendations

| # | Change | Where | Size | Risk |
| --- | --- | --- | --- | --- |
| 1.1 | `recvmsg_x` read batching with adaptive batch (start 4, max 32 on iOS) | `crates/segue-engine/src/tun_fd.rs` `PacketReader` | ~250 lines + tests | Medium: unsafe FFI, must handle `MSG_TRUNC` and short batches |
| 1.2 | `sendmsg_x` write batching, only frames ≤ 4 KiB, gate on estimated utun chain depth | `tun_fd.rs` `write_packet_batch` | ~300 lines | Medium-high: mbuf leak on overflow is a kernel bug; the gate is mandatory |
| 1.3 | Set `UTUN_OPT_MAX_PENDING_PACKETS` from `SO_RCVBUF` | `tun_fd.rs` `TunFd::new` | ~40 lines | Low |
| 1.4 | Raise smoltcp receive ring to 256 KiB and enable window scaling | `tun.rs:5623`, `:5635` | ~30 lines | Medium: memory per flow rises; must be gated by runtime profile |
| 1.5 | Raise `ASSEMBLER_MAX_SEGMENT_COUNT` to 16–32 in the vendored smoltcp | `vendor/smoltcp/src/lib.rs:152` | 1 line + patch note | Low-medium: more per-socket memory (fixed array) |
| 1.6 | Linux GSO/GRO (virtio header, `TUNSETOFFLOAD`) | new `tun_fd` Linux path | ~600 lines | High: large, platform-specific, needs device testing |
| 1.7 | Port the kernel prototype's single-pool accounting into the engine | `tun.rs` + `segue-tun` | Large | High: architectural |

Do 1.1–1.3 first: they are the highest value per line and confined to one
file. 1.4 and 1.5 are cheap and measurable. 1.6 is a separate project.

## 2. iOS NetworkExtension 50 MB budget

### 2.1 What they do

**sing-box** has an explicit OOM-killer service
(`service/oomkiller/`), and it is the most transferable idea in this document.

- Constants: `DefaultAppleNetworkExtensionMemoryLimit = 50 MiB`,
  `DefaultAppleNetworkExtensionGCPercent = 50`
  (`service/oomkiller/policy.go:13-16`).
- On iOS with the OOM killer enabled and no explicit limit, sing-box sets
  `debug.SetGCPercent(50)` and `debug.SetMemoryLimit(RuntimeMemoryLimit(50 MiB))`
  (`experimental/libbox/setup.go:100-112`).
- `RuntimeMemoryLimit` returns the *armed* threshold, not the limit:
  `trigger = limit - 5 MiB`, `armed = limit - 10 MiB`, `resume = limit - 20 MiB`
  (`service/oomkiller/timer.go:28`, `:376-387`).
- The timer polls adaptively (100 ms–10 s), and triggers on either the
  threshold or a **growth-rate projection**: if the current rate would reach
  the limit within `min(2×interval, 1 s)`, it triggers early
  (`service/oomkiller/timer.go:196-224`).
- On trigger it calls `network.ReleaseMemory()` (drops idle connections) and
  then `runtimeDebug.FreeOSMemory()` (`service/oomkiller/timer.go:236-268`).
- Separately, `releaseIdleMemory` calls `FreeOSMemory` when goroutines or
  connections have dropped meaningfully and the process is below the resume
  threshold, at most once per second (`service/oomkiller/timer.go:270-300`).

**sing-tun** contributes the iOS build profile (table in §1.1): 32 KiB base
receive, 256 KiB max, 1 024 flows, 512-entry descriptor ring, 4 reassembly
entries, slab low-water 8. These are compile-time constants selected by
`//go:build ios`, not runtime knobs.

**mihomo** has no iOS-specific work in the available history (no commit
mentions iOS/Darwin). Its memory lever is a build tag: `with_low_memory` halves
`RelayBufferSize` 32 KiB→16 KiB and `UDPBufferSize` 16 KiB→8 KiB
(`common/pool/buffer_standard.go:8,13` vs `buffer_low_memory.go:8,13`). Its
notable recent memory commit is `0455d0d` (2026-11), which moved an embedded
core off the Go heap and reports VmRSS dropping from 389.9→205.1 MiB at 200
flows — a reminder that in Go the allocator, not the algorithm, often dominates.

### 2.2 What Segue does today

- Runtime profiles `LowMemory` / `Mobile` / `MobilePlus` / `Desktop` /
  `Throughput` (`crates/segue-engine/src/lib.rs:197-205`) select flow budgets
  (`tun.rs:150-270`), queue depths (`lib.rs:285-311`) and a transport
  `MemoryClass` (`crates/segue-transport/src/memory_class.rs:12-53`).
- The low-memory profile caps remote buffers at 20 MiB and 128 TCP flows
  (`tun.rs:246-260`).
- There is **no** process-level memory watchdog, no GC tuning (Rust has no
  equivalent), and no reaction to platform memory-pressure notifications in the
  core. `docs/benchmarks.md:500-536` says the guardrails are designed to catch
  transport-buffer regressions "not to claim a universal Network Extension
  memory ceiling".

### 2.3 Gap

Segue's budgets are static per profile. sing-box's insight is that a static
budget cannot know how close the process is to jetsam; a watchdog that watches
actual usage and *growth rate* and sheds idle connections before the limit is
the difference between a warning and a kill. Segue also has no equivalent of
"drop idle connections when memory is tight" as a first-class action.

### 2.4 Recommendations

| # | Change | Where | Size | Risk |
| --- | --- | --- | --- | --- |
| 2.1 | Memory watchdog task: sample RSS (Darwin `task_info`, Android `/proc/self/statm`), trigger at `limit − 5 MiB`, shed idle connections, log | new `crates/segue-engine/src/memory_watch.rs` | ~300 lines | Low-medium: platform FFI; must not itself allocate |
| 2.2 | Growth-rate projection trigger (same formula as sing-box) | same | ~60 lines | Low |
| 2.3 | Expose "release idle memory" on the connection registry and call it from the watchdog | `crates/segue-engine/src/connection.rs` | ~100 lines | Low |
| 2.4 | Make the 50 MiB limit a host-supplied runtime option, defaulting to 50 MiB on iOS | `crates/segue-engine/src/lib.rs` `TunRuntimeOptions` | ~40 lines | Low |

This is the highest-value item in the whole study for iOS stability, and it is
small. It does not require touching the data plane.

## 3. DNS

### 3.1 What sing-box does

- **Rule engine with `evaluate` / `race` / `respond`.** DNS rules are a small
  program (`dns/router.go:583-771`). `evaluate` launches a query against a
  named server and stores the future under a tag
  (`dns/router.go:665-687`); `respond` returns a stored or anonymous response
  (`:688-720`). `race` on a rule with `match_response` arms the rule and
  continues walking, so several candidate answers are fetched in parallel and
  the first matching rule wins (`dns/router.go:593-633`). `speculative` fires
  the query but only uses it if no race rule matches (`:674-687`). Validation
  rejects `evaluate` against a fakeip server (`:1674-1704`).
- **Optimistic cache.** `optimistic` is a bool-or-object with a default window
  of 3 days (`dns/router.go:76-84`). A stale hit is returned with TTL
  normalised to 1 and a background refresh is fired
  (`dns/client.go:307-325`, `:597-655`). Cache capacity is
  `max(CacheCapacity, 1024)` (`dns/client.go:70`), keyed by question +
  transport tag + client subnet + environment (`:92-97`), with single-flight
  (`:299-344`). A persistent bbolt backend exists
  (`experimental/cachefile/dns_cache.go:12-70`).
- **Fake-IP.** A/AAAA only, TTL 600 s (`dns/transport/fakeip/fakeip.go:56-79`).
  Allocation is **sequential and unbounded within the prefix** — there is no
  TTL, expiry or eviction for fake-IP entries
  (`dns/transport/fakeip/store.go:65-71`, `:118-168`). There is no
  `fakeip-filter` in the tree at all.
- **`independent_cache`** is deprecated and unused; the cache is already keyed
  per transport (`dns/router.go:70-72`).

### 3.2 What mihomo does

- Fake-IP pool is **hard-coded to 1 000 entries** for v4 and v6
  (`config/config.go:1545`, `:1557`), backed by two LRUs with cross-touch
  (`component/fakeip/memory.go:15-52`). Default range `198.18.0.1/16`, TTL 1 s
  (`config/config.go:513-514`).
- `fake-ip-filter` with three modes — blacklist, whitelist, rule
  (`component/fakeip/skipper.go:19-35`); fallback nameserver domains are
  auto-injected into the skip set (`config/config.go:1509-1521`).
- Stale-while-revalidate: expired entries return TTL 1 and refresh in the
  background (`dns/resolver.go:169-182`); LRU is created `WithStale(true)`
  (`:496`). Cache default 4 096, LRU or ARC (`:488-498`).
- `respect-rules` tags nameservers with a pseudo-proxy `"RULES"` and runs the
  normal rule engine at dial time (`tunnel/dns_dialer.go:18`, `:57-69`).
- Sniffer has a hard 64 KiB buffer bound and a 1 s budget
  (`component/sniffer/dispatcher.go:24-27`, `:203-299`), plus a skip-list after
  more than 5 failures (`:140-145`).

### 3.3 What Segue does today

- **Kernel prototype** (`crates/segue-kernel/src/dns.rs`, 2 097 lines): domestic
  upstreams raced in parallel, first complete answer wins
  (`dns.rs:387-420`); optimistic cache with `MAX_STALE = 1 h`
  (`dns.rs:75`, `:240-320`); `strip_ech` removes the `ech` SvcParam so the SNI
  sniffer can route (`dns.rs:769-820`); fake-IP pool with a 16 384-entry
  default, TTL-based lease index and durable journal
  (`crates/segue-kernel/src/fakeip.rs:58-88`, `:180-290`).
- **Production engine** (`crates/segue-engine/src/dns.rs`, 3 374 lines +
  `crates/segue-transport/src/dns.rs`): Xray-compatible name-server policies,
  `parallelQuery` (`segue-transport/src/dns.rs:1680-1700`), `serveStale` /
  `serveExpiredTTL` (`crates/segue-config/src/parser/dns.rs:354-370`), a
  256-entry resolver cache (`segue-transport/src/dns.rs:244`), and a fake-IP
  mapper with a lease index and eviction
  (`crates/segue-engine/src/fake_dns.rs:180-290`).
- **No `evaluate`/`race`/`respond` rule actions.** Routing is Xray's rule
  model (`crates/segue-config/src/model.rs:344+`), not sing-box's DNS program.
- **No fake-IP filter.** `DnsFakeIpConfig` has only `enabled`, `ipv4_pool`,
  `pool_size`, `ttl` (`crates/segue-config/src/model.rs:333-338`).

### 3.4 Gap

Segue's DNS is already close to sing-box on the two things that matter most
(optimistic cache, parallel queries) and ahead on fake-IP durability. The real
gaps are:

1. **No fake-IP filter.** Every name gets a fake IP, including connectivity
   checks and NTP, which then fail or behave oddly. mihomo's three-mode filter
   is the right shape.
2. **No response-based routing.** sing-box's `evaluate` + `match_response`
   lets a rule say "if the answer is in this CIDR, route it there" without a
   second resolution. Segue approximates this with `IpIfNonMatch`
   (`crates/segue-engine/src/outbound.rs:3576`), which re-resolves.
3. **Cache size.** 256 entries is small for a phone with many apps; mihomo
   defaults to 4 096 and sing-box to ≥1 024.

### 3.5 Recommendations

| # | Change | Where | Size | Risk |
| --- | --- | --- | --- | --- |
| 3.1 | `fakeIp.filter` with blacklist/whitelist/rule modes | `crates/segue-config/src/model.rs:333`, `crates/segue-engine/src/fake_dns.rs` | ~250 lines | Low |
| 3.2 | Raise the resolver cache to 1 024–4 096 entries, profile-scaled | `crates/segue-transport/src/dns.rs:244` | ~20 lines | Low (memory) |
| 3.3 | Response-based routing (`evaluate`-like) — only if a real config needs it | `crates/segue-engine/src/outbound.rs` | Large | High |

3.1 and 3.2 are cheap. 3.3 is a config-model change and should wait for
demand; Segue's stated principle is compatibility with Xray, which has no
equivalent.

| Real ECH | `common/tls/std_client.go:107-113`, `utls_client.go:119-125` | — | `tls.ech.config` / `config_path` / `query_server_name` (`option/tls.go:237-241`) |

### 4.2 What Segue has

- **Outbound protocols**: Freedom, DNS, VLESS, VMess, Trojan, Shadowsocks2022,
  Hysteria 2, WireGuard, Blackhole, Loopback, SOCKS, HTTP, MASQUE
  (`crates/segue-config/src/model.rs:1145-1159`). Anything else is a parse
  error (`crates/segue-config/src/parser.rs:1095-1101`).
- **Hysteria2 port hopping**: yes, as Xray's `udpHop` mask
  (`H3UdpHopConfig`, `crates/segue-transport/src/stream/xhttp/h3.rs:205-219`;
  wired at `crates/segue-engine/src/outbound/hysteria.rs:135-152`). This is
  equivalent to sing-box's `server_ports`/`hop_interval`.
- **Chrome QUIC parroting**: yes, and thorough — `crates/segue-transport/src/chrome_parrot.rs`
  reproduces quic-go's Chrome transport parameters and uTLS's Chrome QUIC
  ClientHello, with a random extension order per connection.
- **ECH**: **GREASE only.** `crates/segue-transport/src/utls_shaping.rs:849-867`
  builds a syntactically valid ECH GREASE outer hello (X25519 HPKE key, random
  payload) so DPI cannot distinguish it from real ECH. But no real ECH config
  is ever consumed: `echConfigList` is rejected by the parser
  (`crates/segue-config/tests/parser_tests.rs:216`), and the vendored
  `shaped-rustls` has a complete real-ECH implementation
  (`vendor/shaped-rustls/rustls/src/client/ech.rs:38-107`,
  `ClientConfigBuilder::with_ech` at `client/builder.rs:27-32`) that Segue
  never calls. The kernel prototype goes further and *strips* ECH from DNS
  answers (`crates/segue-kernel/src/dns.rs:769`).

### 4.3 Ranking by value / effort

For users in censored networks, the value ordering is roughly:

1. **AnyTLS** — highest value/effort. It is a TLS-only protocol with a simple
   framing layer, it reuses Segue's existing TLS/REALITY carrier, and it is
   increasingly common in subscription links. sing-box's in-tree code is only
   298 lines because the protocol itself is small.
2. **Real ECH** — high value, *low* effort, because the crypto is already
   vendored. Segue currently sends GREASE, which is indistinguishable from real
   ECH on the wire but provides no actual privacy: the SNI is still in the
   clear. Turning on real ECH is mostly plumbing.
3. **ShadowTLS v3** — medium value, medium effort. It is a TLS-camouflage
   wrapper; Segue already has the TLS shaping machinery.
4. **TUIC v5** — medium value, high effort (new QUIC protocol, congestion
   control, UDP relay modes).
5. **NaiveProxy** — low value for Segue specifically: it depends on Chromium's
   network stack (`cronet-go`), which has no Rust equivalent. Not worth it.

### 4.4 Implementation sketch: AnyTLS

AnyTLS is the top pick. Against Segue's traits:

- **Config**: add `OutboundProtocol::AnyTls` and `OutboundSettings::AnyTls`
  (`crates/segue-config/src/model.rs:1145-1176`), parse `password`,
  `idle_session_check_interval`, `idle_session_timeout`, `min_idle_session`
  in a new `crates/segue-config/src/parser/anytls.rs`, and add a `surface.rs`
  entry. Reuse `StreamCarrier` for the TLS/REALITY carrier
  (`crates/segue-engine/src/outbound/carrier.rs:21-120`) — AnyTLS is
  TLS-only, so `StreamCarrier::new` with `unencrypted_payload = false` is
  exactly right.
- **Wire layer**: a new `crates/segue-proxy/src/anytls/` module with the
  command frame (connect / heartbeat / settings) and the padding scheme. This
  is the only genuinely new code, and it is small.
- **Session pool**: AnyTLS multiplexes streams over a small pool of TLS
  sessions. Segue already has a bounded mux pool
  (`crates/segue-engine/src/outbound/mux.rs:135+`) but it speaks Mux.Cool.
  AnyTLS needs its own pool with `min_idle_session` and idle reaping; model it
  on `mux::Pool` but keep it separate.
- **Outbound**: add `AnyTlsOutbound` to `TcpOutbound`/`UdpOutbound`
  (`crates/segue-engine/src/outbound.rs:403-440`), with `open` /
  `open_udp` mirroring `TrojanOutbound`
  (`crates/segue-engine/src/outbound/trojan.rs:18-180`). UDP rides UoT, which
  Segue already implements for Trojan (`NativeUdpSession`,
  `trojan.rs:150-200`).
- **Health/observatory**: no change; it is a normal TCP outbound.

Estimated size: ~1 200–1 500 lines including tests. Risk: medium — the
protocol is simple but the session pool's idle semantics interact with network
changes, and Segue's fail-closed parser means every field must be validated.

## 5. Rule-sets and health-checked groups

### 5.1 What they do

**sing-box `.srs`** (`common/srs/`): magic `SRS`, zlib-compressed, big-endian
version byte, uvarint rule count (`common/srs/binary.go:25`, `:55-124`).
Format versions 1–5, current 5 (`constant/rule.go:23-30`); the writer
auto-downgrades to the lowest version the used items allow
(`cmd/sing-box/cmd_rule_set_compile.go:84-102`). There is a separate
**memory-mapped format for iOS**, magic `SRSM`, 40-byte header, 24-byte blob
entries (`common/srs/mmap.go:20-26`), loaded via
`route/rule/rule_set_mmap_ios.go:17-44`. Remote rule-sets default to a 24 h
update interval with ETag/`If-None-Match` and a disk cache
(`route/rule/rule_set_remote.go:60-65`, `:243`, `:291`).

**mihomo `.mrs`** (`rules/provider/mrs_reader.go`): magic `MRS\x01`, whole file
zstd-compressed, then `magic | behavior byte | int64 count | int64 extra-len |
extra | payload` (`:12-70`). Domain payload is a succinct trie
(`component/trie/domain_set_bin.go:9-51`); IP-CIDR payload is a runtime-range
array (`component/cidr/ipcidr_set_bin.go:12-36`). Only `domain` and `ipcidr`
behaviors implement `FromMrs` (`rules/provider/mrs_reader.go:16`,
`domain_strategy.go:57`, `ipcidr_strategy.go:58`); `classical` falls through to
`ErrInvalidFormat`.

**Health-checked groups.** sing-box has `selector` and `urltest` only — there
is **no `fallback` group** (`constant/proxy.go:52-53`). `urltest` defaults:
interval 3 m, idle timeout 30 m, tolerance 50 ms, probe timeout 15 s
(`constant/timeout.go:9-15`, `protocol/group/urltest.go:240-246`). It is
**lazy**: the ticker starts on first traffic and stops after `idle_timeout`
(`protocol/group/urltest.go:280-294`, `:354-378`), caps concurrency at 10
(`:416`), and keeps the incumbent unless beaten by more than `tolerance`
(`:310-352`). mihomo's `url-test` has the same tolerance idea
(`adapter/outboundgroup/urltest.go:103-149`) and adds `load-balance` with
consistent hashing, round-robin and sticky sessions
(`loadbalance.go:167`, `:196`, `:220`, `:296-305`).

### 5.2 What Segue does

- **No `.srs`/`.mrs` support.** Routing uses Xray geodata (`.dat`, protobuf)
  via `crates/segue-config/src/geodata.rs` (indexed, bounded, 128 MiB file cap)
  and inline rules. There is no rule-set provider, no remote update, no
  binary rule format.
- **Balancers**: `Random`, `RoundRobin`, `LeastPing`, `LeastLoad`
  (`crates/segue-config/src/model.rs:97-103`), selected in
  `OutboundSelectionOverlay::select` (`crates/segue-engine/src/outbound.rs:2502-2530`).
  Health comes from the observatory (`crates/segue-engine/src/health.rs`),
  which probes on a fixed interval with concurrency 4
  (`health.rs:14`, `:138`) and **no lazy/idle pause**.
- **No `fallback` group** either, but `fallback_tag` exists on selector groups
  (`outbound.rs:2522-2527`).

### 5.3 Gap

1. **Rule-set formats.** Segue cannot consume the `.srs`/`.mrs` files that
   most modern subscription providers ship. This is a compatibility gap, not a
   performance one.
2. **Lazy health checks.** Segue's observatory probes every node every interval
   forever, even when the tunnel is idle. On a phone that is battery and
   radio wakeups. sing-box and mihomo both pause when idle.
3. **Tolerance-based selection.** Segue's `LeastPing` picks the strict minimum
   (`outbound.rs:2595-2608`), so two nodes 1 ms apart flap. sing-box keeps the
   incumbent within 50 ms.

### 5.4 Recommendations

| # | Change | Size | Risk |
| --- | --- | --- | --- |
| 5.1 | Lazy observatory: start on first traffic, stop after an idle timeout | ~150 lines in `health.rs` | Low |
| 5.2 | Tolerance in `LeastPing` (keep incumbent within N ms) | ~40 lines in `outbound.rs:2595` | Low |
| 5.3 | `.srs` reader (v1–v5) for local and remote rule-sets | ~1 200 lines | Medium |
| 5.4 | `.mrs` reader (domain + ipcidr) | ~600 lines | Medium |
| 5.5 | Remote rule-set updater with ETag and disk cache | ~500 lines | Medium |

5.1 and 5.2 are small and improve battery and stability immediately. 5.3–5.5
are a compatibility project; do them only if subscription compatibility is a
product goal.
